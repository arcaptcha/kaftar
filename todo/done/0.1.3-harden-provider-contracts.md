# 0.1.3: Harden Provider Contracts

## Context

Completed migration task [0.1](0.1-migrate-reference-service.md) documented legacy provider behavior that could accept HTTP/API failures, expose credential-bearing URLs, silently ignore extra attachments, outlive cancellation, or send unrestricted outbound webhooks. The owner approved the compatibility and security policy in the [hardening design](../../docs/hardening-design.md).

## Objective

Define, implement, and verify explicit provider success, failure, cancellation, attachment, credential-safety, and outbound destination contracts.

## Scope

Require provider-specific success responses, bounded and cancellable I/O, credential-safe errors, explicit attachment limits, and no caller-owned payload mutation. Replace the context-free SMS client with direct REST use, own SMTP connection cancellation, and make the generic HTTP sender stateless and destination-allowlisted. Use local mocks and protocol fixtures; do not contact real recipients without separate approval.

## Acceptance Criteria

- Compatibility differences and chosen provider behavior are documented and tested.
- HTTP or provider-level failure responses cannot silently count as successful delivery.
- Tokens, credentials, response bodies, and submitted payloads are absent from returned errors and rejection logs.
- Attachment, timeout, cancellation, body-limit, redirect, cookie, proxy, DNS, and destination policies are explicit.
- Full tests, affected image builds, and API/provider documentation pass.

## Validation

- Provider-focused tests passed for Bale, Mattermost, SMS, email, outbound HTTP, and the shared bounded HTTP client. They cover error responses, malformed/oversized bodies, exact long-text boundaries, attachment limits and contents, caller-data preservation, cancellation, stalled I/O, redirect refusal, cookie isolation, proxy independence, credential-safe failures, MIME/CC/BCC behavior, DNS pinning, mixed-address rejection, and explicit private-network exceptions.
- `go -C server test ./... -count=1 -timeout=90s` passed after the final implementation change.
- The full `go -C server test -race ./... -count=1 -timeout=120s` suite passed with the disposable PostgreSQL/RabbitMQ integration environment enabled.
- `go -C server vet ./...`, `go -C server mod verify`, and `go -C server build -o /tmp/kaftar-final ./cmd` passed. The Go 1.26.5 Docker image built and the Compose services became healthy.
- `npx --yes @redocly/cli lint docs/openapi.yaml --extends minimal` passed with only the intentional localhost server URL warning.
- Official Bale, Mattermost, RabbitMQ, Kavenegar REST/client, and Gomail transport/MIME sources were reviewed on September 7, 2026. Exact contract references are recorded in [provider contracts](../../docs/provider-contracts.md).

No real Bale, Mattermost, Kavenegar, SMTP, or arbitrary webhook recipient was contacted. Local mocks establish implemented behavior, not live third-party certification or production readiness.

## Completion Notes

Bale now requires HTTP success, `ok: true`, and a nonzero message ID. Mattermost post/upload operations require HTTP 201 and nonempty result IDs. SMS uses a context-aware Kavenegar REST request and validates both API-level and per-recipient acceptance. Email retains Gomail MIME construction but uses an owned SMTP connection with deadlines, cancellation-driven closure, implicit TLS on port 465, STARTTLS otherwise, and authentication only after verified TLS.

Bale and Mattermost reject multiple or empty attachments before network activity while retaining their documented compatibility thresholds. Provider errors avoid request URLs, tokens, passwords, response bodies, and payload content.

The generic HTTP sender is deny-by-default. Operators must allow exact `host:port` destinations; private destinations additionally require an allowed private CIDR. Every resolved address is checked, mixed allowed/blocked answers are rejected, dialing is pinned to a checked IP, redirects/cookies/environment proxies are disabled, and userinfo, fragments, Host overrides, and hop-by-hop headers are rejected. Body limits are documented in [provider contracts](../../docs/provider-contracts.md).

Archived with its immutable prefix after owner approval, implementation, documentation, and validation. Provider SDKs remain outside this repository by owner decision.
