# 0.1.2: Review Delivery Reliability

## Context

The migrated service inherited publication without confirms, database/broker inconsistency, unsafe acknowledgment paths, unenforced deduplication, incomplete shutdown, concurrent connection reuse, and misleading delivery state fields. The approved [hardening design](../../docs/hardening-design.md) defines the required corrections.

## Objective

Implement and verify explicit durability, retry, recovery, idempotency, and shutdown guarantees without claiming exactly-once external delivery.

## Scope

Use PostgreSQL as the delivery source of truth, reconcile accepted rows to RabbitMQ, publish persistent mandatory notifications with confirms, fence provider attempts with expiring leases, persist transitions before acknowledgment, and drain bounded work during shutdown. Preserve the HTTP 200 submission contract while making database commit its acceptance boundary. Add channel-scoped idempotency for HTTP and direct AMQP submissions with canonical request comparison and conflict rejection.

## Acceptance Criteria

- Each inherited failure gap has a deterministic regression and approved disposition.
- Publish/commit failures, restarts, duplicates, reconnects, scheduling, lease expiry, and SIGTERM behavior are documented and tested.
- Identical keyed submissions return one ID; conflicting submissions return HTTP 409 or are rejected from AMQP without requeue.
- Delivery transitions are database-authoritative, fenced, and committed before broker settlement.
- Behavioral fixes pass focused, full, race, integration, image, and contract validation.

- The full `go -C server test -race ./... -count=1 -timeout=120s` suite passed against disposable PostgreSQL and RabbitMQ fixtures. Scenarios cover concurrent keyed submissions and claims, deferred commit failure, commit-before-publish recovery, reconnect, ambiguous provider completion, unroutable confirmed publication, scheduling order, lease fencing, and graceful drain.
- A disposable Compose runtime check passed HTTP idempotent replay and HTTP 409 conflict handling, acceptance while RabbitMQ was stopped, recovery after server and broker restart, and real SIGTERM draining. The active slow delivery completed and the container exited with code 0 in 1.28 seconds.
- `go -C server vet ./...`, `go -C server mod verify`, and `go -C server build -o /tmp/kaftar-final ./cmd` passed. The Go 1.26.5 Docker image built and the Compose services became healthy.

- Rejected or transient AMQP ingestion paths now emit payload-free warnings; a focused regression verifies malformed payload content is absent from log fields and messages.

No production database was migrated and no exactly-once provider guarantee is claimed. External provider success followed by a failed completion commit can still produce a duplicate attempt during recovery.

## Completion Notes

The database commit is the acceptance boundary. A one-second reconciler reserves due rows and publishes ID/channel notifications with mandatory delivery, confirms, returns, and finite deadlines. Workers load authoritative rows, acquire 60-second fenced claims, apply 30-second provider attempt deadlines, and persist success/retry/dead transitions before acknowledging.

Idempotency keys are immutable row data, scoped by channel, limited to nonempty printable ASCII without spaces, and enforced by a partial unique database index. Canonical comparison uses validated typed message JSON plus normalized retries, UTC microsecond scheduling, and normalized HTTP method/URL options. Empty keys intentionally provide no deduplication guarantee. Retention must preserve keyed rows for the documented deduplication window or explicitly redefine that window.

The transactional migration refuses legacy duplicate keys and nonempty legacy keys without fingerprints instead of silently merging data. Backfill preserves terminal states and turns inherited sending rows into expired recoverable attempts. Operators must stop old consumers and back up the database before rollout.
