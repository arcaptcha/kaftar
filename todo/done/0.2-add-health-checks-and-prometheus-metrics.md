# 0.2: Add Health Checks and Prometheus Metrics

## Context

The current `GET /health` endpoint returns the JSON string `"Ok"` when the HTTP handler is
reachable. It does not verify PostgreSQL, RabbitMQ, delivery workers, enabled provider services,
or shutdown state. Docker Compose therefore can report the server as healthy while it cannot
accept, persist, publish, or deliver messages. The service also has no Prometheus endpoint or
stable operational metrics for request traffic, delivery outcomes, retries, or dependency health.

## Objective

Implement bounded, machine-readable liveness and readiness checks for required dependencies and
delivery services, and expose low-cardinality Prometheus metrics that operators can use to detect
availability, backlog, retry, and provider failures.

## Scope

- Add `GET /health/live` for process liveness without remote dependency checks.
- Add `GET /health/ready` for aggregate readiness and keep `GET /health` as a compatibility alias
  to the readiness result.
- Check PostgreSQL connectivity, RabbitMQ connectivity, required messaging topology, delivery
  worker state, shutdown state, and every enabled provider service.
- Classify each check as required or informational. Required dependency or internal service
  failures must make readiness return HTTP 503. Enabled provider degradation must be visible, and
  its effect on aggregate readiness must be explicit and documented.
- Use concurrent checks with overall and per-check timeouts. Health requests must not hang, create
  unbounded work, publish messages, send provider traffic with side effects, or expose raw errors.
- Return stable JSON containing aggregate status and per-component status, criticality, duration,
  and a sanitized reason code. Do not return credentials, connection strings, payloads, recipient
  data, provider response bodies, or internal network details.
- Mark readiness unavailable before graceful shutdown begins and restore healthy status after
  transient dependency recovery without restarting the process.
- Add `GET /metrics` using the maintained Prometheus Go client and its standard exposition content
  type. Register collectors once and make repeated test/application construction safe.
- Instrument HTTP request count, duration, and in-flight requests using normalized route, method,
  and status labels.
- Instrument message submissions, delivery attempts, successful deliveries, permanent failures,
  retries, dead messages, and delivery duration using bounded channel and outcome labels.
- Export dependency and service health, check duration, worker readiness, publish/consume errors,
  and a build-information metric.
- Export useful outbox backlog size and oldest pending age metrics through a bounded or cached
  collector so Prometheus scrapes cannot overload PostgreSQL.
- Avoid labels containing message IDs, queue-generated identifiers, URLs, hosts, recipients,
  tenant data, error text, or any other unbounded or sensitive values.
- Update Docker Compose to probe the readiness endpoint. Document endpoint semantics, metric names,
  label contracts, timeout configuration, scrape guidance, and troubleshooting behavior.
- Update the OpenAPI contract, `README.md`, development documentation, and example environment
  configuration in the same implementation change.

## Acceptance Criteria

- Liveness returns HTTP 200 while the process can serve requests, independent of dependency
  outages, and becomes unavailable during shutdown.
- Readiness checks PostgreSQL, RabbitMQ, messaging topology, workers, and every enabled provider
  service, returning HTTP 200 only when all checks classified as required are healthy.
- A failed, timed-out, disabled, degraded, and recovered component has a deterministic documented
  representation in the health response.
- Health checks complete within configured bounds and do not perform destructive or externally
  visible provider actions.
- Health responses and logs expose no secrets, payloads, provider bodies, or raw infrastructure
  addresses and errors.
- `/health` remains usable by existing deployments while reporting the new readiness semantics.
- `/metrics` is valid Prometheus exposition output and includes the scoped HTTP, delivery,
  dependency, service, worker, backlog, and build metrics.
- Metric names, types, help text, units, and bounded label sets are documented and covered by tests.
- Repeated server construction, tests, and shutdown do not panic because of duplicate collector
  registration, leaked goroutines, or stale health state.
- Tests cover healthy operation, each required dependency failure, worker failure, provider
  degradation, timeout behavior, shutdown, recovery, metric increments, and label cardinality.
- Docker Compose reports the server unhealthy when readiness fails and healthy again after its
  required dependencies and internal services recover.
- The full server test suite, race detector, vet, build, image build, Compose health checks, and
  OpenAPI validation pass.

## Validation

Completed September 11, 2026.

- `go -C server test ./... -count=1 -timeout=90s` passed.
- `go -C server test -race ./... -count=1 -timeout=120s` passed.
- `go -C server vet ./...`, `go -C server mod verify`, and the server build passed.
- The standalone server image built successfully with Docker Compose.
- An isolated Compose project became healthy and served liveness, readiness, and metrics.
- Stopping PostgreSQL made readiness return HTTP 503 while liveness stayed HTTP 200. Docker marked
  the server unhealthy, then readiness and Docker health recovered after PostgreSQL restarted.
- The same HTTP, Docker health, and recovery checks passed while stopping and restoring RabbitMQ.
- Local fakes covered dependency timeout and recovery, disconnected workers, provider degradation,
  shutdown liveness, sanitized reasons, duplicate registry construction, metric increments, bounded
  HTTP labels, and cached outbox statistics.
- `npx --yes @redocly/cli lint:docs` was not used because the repository has no wrapper script.
  `npx --yes @redocly/cli lint docs/openapi.yaml --extends minimal` passed with only the intentional
  localhost server URL warning.

No provider health check contacted Bale, email, Mattermost, SMS, or outbound HTTP destinations. The
isolated Compose database and broker used project-specific empty volumes and were removed afterward.

## Completion Notes

`/health/live` now reports process and shutdown state without remote calls. `/health/ready` checks
PostgreSQL, RabbitMQ connectivity and queue topology, the relay, and enabled consumers concurrently
within configured bounds. `/health` remains as a readiness alias, although its response body is now
the structured report rather than the legacy JSON string.

Provider components are informational. Disabled providers report `disabled`; enabled providers
report `degraded` with `remote_unverified` because no safe universal non-mutating remote probe
exists. This avoids orchestrator restart loops during third-party outages while delivery metrics
expose the actual provider failure rate.

Metrics use a private Prometheus registry per application. HTTP methods and route templates,
channels, outcomes, operations, workers, states, and health components have bounded labels. The
background outbox collector uses configurable refresh and query bounds, retains the last successful
values on failure, and exposes freshness metrics.

The complete endpoint, component, metric, label, configuration, and alerting contract is recorded in
[health checks and Prometheus metrics](../../docs/observability.md).
